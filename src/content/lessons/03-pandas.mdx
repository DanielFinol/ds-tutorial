Once data is out of the warehouse, pandas is where most analysis happens. This lesson drills the idioms you'll use daily, on current pandas (version 3), where two long-standing sources of bugs have changed: text columns are a real `str` type, and **copy-on-write** is always on.

## Assign with `.loc`, not through a chain

With copy-on-write, every indexing result behaves like a copy. The classic chained assignment below now changes nothing (pandas warns you). Do the selection and the assignment in **one** `.loc` call.

<PyCell code={`
df = orders.head(5).copy()

df[df["total"] > 100]["status"] = "big"             # modifies a temporary copy: no effect
print(df["status"].tolist())

df.loc[df["total"] > 100, "status"] = "big"         # one .loc call: works
print(df["status"].tolist())
`} />

## Method chains

A chain reads top to bottom as a recipe, leaves no half-finished variables behind, and is easy to review. The tools: `query`/boolean filters, `assign` (with a `lambda` to refer to the frame so far), `groupby().agg()` with named aggregations, and `pipe` for your own functions.

<PyCell code={`
(
    orders
    .query("status == 'completed' and order_ts >= '2024-01-01'")
    .assign(
        month=lambda d: d["order_ts"].dt.to_period("M"),
        discounted=lambda d: d["discount_pct"] > 0,
    )
    .groupby("month")
    .agg(
        orders=("order_id", "count"),
        revenue=("total", "sum"),
        discounted_share=("discounted", "mean"),
    )
    .round(2)
    .tail(4)
)
`} />

## Group-wise columns: `transform`, `cumcount`, `diff`

`agg` collapses each group to one row. When you need a value **per original row** that depends on its group (the pandas equivalent of a SQL window function), use `transform` and friends. They return a result aligned to the original index.

<PyCell code={`
seq = completed.sort_values(["customer_id", "order_ts"]).copy()
g = seq.groupby("customer_id")

seq["customer_revenue"] = g["total"].transform("sum")            # sum(...) OVER (PARTITION BY customer_id)
seq["share_of_customer"] = seq["total"] / seq["customer_revenue"]
seq["running_total"] = g["total"].cumsum()                       # running sum within customer
seq[["customer_id", "order_ts", "total", "share_of_customer", "running_total"]].head(6).round({"share_of_customer": 3, "running_total": 2})
`} />

## Reshaping: long to wide and back

Stakeholders read wide tables; analysis wants long ones. `pivot_table` goes wide, `melt` goes long.

<PyCell code={`

    completed

    .pivot_table(index="quarter", columns="device", values="total", aggfunc="sum", margins=True, margins_name="all")

## Time series: `resample` and `rolling`

With a datetime index, `resample` is a time-aware `groupby` (and it keeps empty periods, which `groupby` on a truncated date silently drops). `rolling` smooths.

<PyCell code={`
daily = completed.set_index("order_ts")["total"].resample("D").sum()
print(daily.tail(3), "\\n")
print("days with zero revenue kept in the series:", int((daily == 0).sum()))
`} />

## Vectorise: never loop over rows

`apply(axis=1)` and `iterrows` call Python once per row. On the item table that is over a hundred thousand calls. Column arithmetic does the same work in compiled code.

<PyCell code={`
import time

items = order_items.merge(products[["product_id", "category", "price", "unit_cost"]], on="product_id", validate="many_to_one")
sample = items.head(20_000)

t0 = time.perf_counter()
slow = sample.apply(lambda r: r["quantity"] * (r["unit_price"] - r["unit_cost"]), axis=1)
t_slow = time.perf_counter() - t0

t0 = time.perf_counter()
fast = sample["quantity"] * (sample["unit_price"] - sample["unit_cost"])
t_fast = time.perf_counter() - t0

print(f"apply(axis=1): {t_slow * 1000:7.1f} ms")
print(f"vectorised:    {t_fast * 1000:7.1f} ms   ({t_slow / t_fast:,.0f}x faster, same result: {slow.round(6).equals(fast.round(6))})")
`} />

**6.** The pricing team's script below assigns a discount tier row by row with `apply`. `items` already has the product's list `price`. Replace it with a vectorised version using `numpy.select` that stores the same values in `items["tier"]`: `"deep"` when the unit price is below 75% of the product's list `price`, `"light"` when it is below 100% of it, otherwise `"full"`.

<PyCell

import numpy as np

def tier(row):  # slow, row by row
    ratio = row["unit_price"] / row["price"]
    if ratio < 0.75:
        return "deep"
    if ratio < 1:
        return "light"
    return "full"

items["tier"] = ...   # vectorised: no apply, no loop
items["tier"].value_counts()
`}
  check={`
assert "tier" in items.columns and not isinstance(items["tier"].iloc[0], type(...)), "assign the vectorised result to items['tier']"
_r = items["unit_price"] / items["price"]
_e = np.select([_r < 0.75, _r < 1], ["deep", "light"], default="full")
assert (items["tier"].astype(str).to_numpy() == _e).all(), "tiers differ: ratio = unit_price / price; < 0.75 deep, < 1 light, else full"
`}
  hint="`ratio = items['unit_price'] / items['price']`, then `np.select([ratio < 0.75, ratio < 1], ['deep', 'light'], default='full')`. Conditions are checked in order."
  solution={`
import numpy as np

ratio = items["unit_price"] / items["price"]
items["tier"] = np.select([ratio < 0.75, ratio < 1], ["deep", "light"], default="full")
items["tier"].value_counts()

## Types and memory

Check `dtypes` after every load. Low-cardinality text as `category` and right-sized integers routinely halve memory (far more on wide, text-heavy tables), which is often the difference between "fits in RAM" and "doesn't".

<PyCell code={`
before = orders.memory_usage(deep=True).sum()
slim = orders.astype({"status": "category", "device": "category", "discount_pct": "int8", "customer_id": "int32", "order_id": "int32"})
after = slim.memory_usage(deep=True).sum()
print(f"{before / 1e6:.1f} MB -> {after / 1e6:.1f} MB")
slim.dtypes
`} />
