Notebooks are where analysis starts. They are a poor place for it to live: hidden state, no tests, impossible to review. The single biggest step up in professional practice is this routine: **explore in a notebook, then move anything you'll reuse into functions in a module, with tests, under version control.**

This lesson does the Python half in the browser (real `pytest` runs here) and the git half on your machine.

## 1. Extract a function

A good analysis function takes everything it needs as **arguments**, returns a value, touches no globals, doesn't modify its inputs, and validates what could plausibly go wrong.

**1.** Write `monthly_revenue(orders, start, end)`. It returns a DataFrame with one row per month and columns `month` (a monthly `Period`), `orders` and `revenue`, for **completed** orders with `start <= order_ts < end` (half-open). It must raise `ValueError` if `start` is not before `end`, and must not modify `orders`.

<PyCell
  code={`
def monthly_revenue(orders: pd.DataFrame, start: str, end: str) -> pd.DataFrame:
    """Completed-order count and revenue per month for start <= order_ts < end."""
    ...

monthly_revenue(orders, "2024-10-01", "2025-01-01")
`}
  check={`

_r = monthly_revenue(_o, "2024-10-01", "2025-01-01")
_c = _o[(_o["status"] == "completed") & (_o["order_ts"] >= "2024-10-01") & (_o["order_ts"] < "2025-01-01")]

dsw.same(_r.assign(month=_r["month"].astype(str)) if "month" in _r.columns else _r.reset_index().assign(month=lambda d: d["month"].astype(str)), _e.assign(month=_e["month"].astype(str)))
assert list(_o.columns) == list(dsw.load("orders").columns), "the function added a column to its input: work on a filtered copy"
try:
    monthly_revenue(_o, "2025-01-01", "2024-10-01")
except ValueError:
    pass
else:
    raise AssertionError("start after end should raise ValueError")
assert len(monthly_revenue(_o, "2030-01-01", "2030-02-01")) == 0, "a period with no orders should return an empty frame, not fail"
`}
  hint="Convert with `pd.Timestamp(start)`; `if start >= end: raise ValueError(...)`; filter with one boolean mask (this gives a new frame, so `.assign(month=...)` is safe); then `groupby('month').agg(orders=('order_id', 'count'), revenue=('total', 'sum')).reset_index()`."
  solution={`
def monthly_revenue(orders: pd.DataFrame, start: str, end: str) -> pd.DataFrame:
    """Completed-order count and revenue per month for start <= order_ts < end."""
    start, end = pd.Timestamp(start), pd.Timestamp(end)
    if start >= end:
        raise ValueError(f"start ({start.date()}) must be before end ({end.date()})")
    mask = (orders["status"] == "completed") & (orders["order_ts"] >= start) & (orders["order_ts"] < end)
    return (
        orders[mask]
        .assign(month=lambda d: d["order_ts"].dt.to_period("M"))
        .groupby("month")
        .agg(orders=("order_id", "count"), revenue=("total", "sum"))
        .reset_index()
    )

monthly_revenue(orders, "2024-10-01", "2025-01-01")
`}

## 2. Move it into a module

Functions you'll reuse belong in a `.py` file inside a package, where they can be imported by notebooks, scripts and tests alike. A typical small project looks like this:

```text
bramble-analysis/
├── pyproject.toml        # dependencies and tool settings (uv)
├── uv.lock
├── src/bramble/          # your importable package
│   ├── __init__.py
│   └── metrics.py
├── tests/
│   └── test_metrics.py
├── notebooks/            # exploration only; imports from bramble
└── data/                 # not committed (listed in .gitignore)
```

The cell below creates the package in this browser session's file system and imports from it, exactly as you would locally.

<PyCell code={`

## 3. Test it

A test builds a **tiny input by hand**, calls the function, and asserts the exact expected output. Hand-made data is the point: you can see the right answer, and every edge case can be planted deliberately. Here is one test to start from, run with real pytest:

import pandas as pd
import pytest
from bramble.metrics import monthly_revenue


def make_orders(rows):
    return pd.DataFrame(rows, columns=["order_id", "order_ts", "status", "total"]).assign(
        order_ts=lambda d: pd.to_datetime(d["order_ts"])
    )


def test_sums_revenue_per_month():
    orders = make_orders([
        (1, "2024-01-10", "completed", 10.0),
        (2, "2024-01-20", "completed", 5.0),
        (3, "2024-02-01", "completed", 7.0),
    ])
    result = monthly_revenue(orders, "2024-01-01", "2024-03-01")

def test_only_completed_orders_count():
    orders = make_orders([
        (1, "2024-01-10", "completed", 10.0),
        (2, "2024-01-11", "cancelled", 99.0),

<Lab title="The git workflow you'll use every day" time="20 min">

Every team works the same way: **one branch per change, small commits, a pull request, review, merge.** In your `bramble-analysis` project:

```bash
git init
printf ".venv/\ndata/\n__pycache__/\n.ipynb_checkpoints/\n*.joblib\n.env\n" > .gitignore
git add . && git commit -m "Initial project"

git switch -c monthly-revenue-metric          # 1. branch
mkdir -p src/bramble tests                    # 2. add metrics.py and test_metrics.py from this lesson
uv add --dev pytest ruff
uv run pytest                                 # 3. tests pass locally
git add src tests pyproject.toml uv.lock
git commit -m "Add monthly_revenue metric with tests"
git push -u origin monthly-revenue-metric     # 4. then open a pull request on GitHub or GitLab
```

Things that mark you as someone who has done this before: commits that each do one thing, with a message saying *what and why*; never committing data, credentials or `.venv`; `git pull --rebase` before pushing; and notebooks committed with outputs cleared (`uv run jupyter nbconvert --clear-output --inplace notebooks/*.ipynb`, or the `nbstripout` tool).

To make `from bramble.metrics import ...` work from `src/`, add this to `pyproject.toml` and run `uv sync`:

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/bramble"]
```

<Lab title="Automate the checks: ruff, pre-commit and CI" time="15 min">

**ruff** is the standard linter and formatter; it replaces flake8, isort and black, and runs in milliseconds:

```bash
uv run ruff check --fix .     # lint: unused imports, undefined names, likely bugs
uv run ruff format .          # format: no more style debates in review
```

Run them automatically before every commit with **pre-commit** (`uv add --dev pre-commit`, then `uv run pre-commit install`), configured in `.pre-commit-config.yaml`:

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.8.0          # use the latest release tag
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
```

And run the tests on every pull request with **continuous integration**. On GitHub, save this as `.github/workflows/ci.yml`:

```yaml
name: CI
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v6      # use the latest major version
      - run: uv sync --locked
      - run: uv run ruff check .
      - run: uv run pytest
```

Push a branch with a deliberately failing test and watch the pull request go red. That red cross, visible to the reviewer, is what makes tests worth writing.

</Lab>

## Reviewing a pull request

Half of the workflow is reading other people's changes. A reviewer of data code checks, in this order:

1. **Is it correct?** Join keys and grain, date boundaries, filters, what happens with missing values and empty inputs.
2. **Is it tested?** A test that would fail if the logic were wrong, not just one that runs.
3. **Is it reproducible?** No hard-coded local paths, no hidden state, dependencies locked, random seeds set.
4. **Is it readable?** Names that say what things are; a reader can follow it without the author present.
5. **Is anything leaking?** No credentials, no customer data in the repository or in notebook outputs.

Comment on the code, not the person; ask questions where you're unsure ("what happens here if `orders` is empty?"); approve when it's better than what's there, not when it's perfect.
